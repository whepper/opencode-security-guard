# Incident: Shell RC File Credential Exposure

## Summary

On 2026-08-21 an agent read `~/.zshenv` using otherwise permitted shell reads while debugging a PATH issue.

The file contained two plaintext API keys. Their values entered tool output and were transmitted to the model provider twice.

No protected filename was accessed. The existing four security layers therefore behaved as configured.

## Root cause

The controls relied heavily on filename signals.

`.zshenv` is a shell configuration file, but its name does not inherently indicate that it contains secrets.

This exposed a broader problem:

> A filename-based policy cannot reliably classify every file that may contain credentials.

## Remediation

The following controls were added:

- hard deny for `~/.config/secrets/`;
- approval-gated access to shell RC files;
- approval-gated shell references to those files;
- watcher exclusions for relevant RC files;
- explicit policy guidance identifying RC files as potentially sensitive;
- migration of credentials from `.zshenv` to `~/.config/secrets/shell.env` with restrictive permissions.

## Credential response

The exposed keys must be considered compromised and rotated. Local remediation cannot undo provider-side transmission.

## Lessons

1. Secret protection needs both filename and semantic controls.
2. Shell configuration deserves explicit treatment.
3. Watcher exclusions are not sufficient.
4. Agent policy is not an enforcement boundary.
5. Every discovered bypass should become a regression test.
6. Security controls need continuous verification after OpenCode/plugin upgrades.

This incident is retained as a security case study rather than hidden because it demonstrates the limits of the design honestly.
